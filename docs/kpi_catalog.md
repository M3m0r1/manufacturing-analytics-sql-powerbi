# Каталог KPI

Тут описано, як рахується кожен показник: що в чисельнику, що в знаменнику, в яких одиницях і де він є в SQL та Power BI. Дані синтетичні, а значення взяті з повного запуску проєкту.

## Як я рахую

1. Рахую вироби, а не рядки таблиць. У SQL для цього `COUNT(DISTINCT unit_id)`, у DAX `DISTINCTCOUNT`.
2. У виробу один остаточний статус, `Good` або `Rejected`. Повторні тести його не змінюють.
3. Дефект і брак це різні речі. Виріб із виправленим дефектом лишається придатним.
4. Якщо таблиці мають різну деталізацію (наприклад, план по днях і вироби по одному), я спершу зводжу кожну до спільного рівня, а потім з'єдную. Інакше рядки множаться і суми виходять завищеними.
5. Ділю безпечно: `NULLIF` у SQL і `DIVIDE` у DAX, щоб нуль у знаменнику не давав помилку.

## Повторні тести

| Правило | Як зроблено |
|---|---|
| Рахуємо вироби, не спроби | `COUNT(DISTINCT unit_id)` |
| FPY дивиться тільки на першу спробу | `attempt_no = 1 AND result = 'Pass'` |
| Retest Rate рахує вироби з двома й більше спробами | `MAX(attempt_no) >= 2` |
| Остаточний статус лежить у `units.final_status` | звіряється з останньою спробою через `ROW_NUMBER() OVER (PARTITION BY unit_id ORDER BY attempt_no DESC)` |
| Максимум спроб | 3 |
| Номери спроб йдуть підряд | перевірка `COUNT(*) = MAX(attempt_no)` |

## Показники

### K1. Planned Units

План випуску придатних виробів.

| | |
|---|---|
| Формула | `SUM(planned_good_units)` |
| Одиниця | шт. |
| Джерело | `production_plan` |
| DAX | `Planned Units` |
| Значення | 164 684 |

План задано саме в придатних виробах, тому порівнювати його із запущеними (Produced) не можна.

### K2. Produced Units

Скільки виробів запущено.

| | |
|---|---|
| Формула | кількість виробів у `units` |
| Одиниця | шт. |
| DAX | `Produced Units` (`COUNTROWS(units)`) |
| Значення | 165 885 |

### K3. Good Units

Скільки з них придатних.

| | |
|---|---|
| Формула | вироби зі статусом `Good` |
| Одиниця | шт. |
| DAX | `Good Units` |
| Значення | 153 881 |

### K4. Plan Achievement %

| | |
|---|---|
| Формула | Good Units / Planned Units × 100 |
| Одиниця | % |
| DAX | `Plan Achievement %` |
| Значення | 93.44% |

Ділю саме придатні, а не всі запущені. Якби я брав усі запущені, брак ховав би недовиконання плану. Якщо плану немає (нуль), результат порожній.

### K5. Variance to Plan

| | |
|---|---|
| Формула | Good Units − Planned Units |
| Одиниця | шт. (мінус означає, що план не виконано) |
| DAX | `Variance to Plan` |
| Значення | −10 803 |

### K6. Scrap Rate %

| | |
|---|---|
| Формула | Rejected Units / Produced Units × 100 |
| Одиниця | % |
| DAX | `Scrap Rate %` |
| Значення | 7.24% (12 004 з 165 885) |

Це частка забракованих виробів, а не частка виробів із дефектами. Тому показник названо Scrap Rate, а не Defect Rate.

### K7. First Pass Yield %

| | |
|---|---|
| Чисельник | вироби, у яких перша спроба тесту успішна |
| Знаменник | вироби, які тестувалися |
| Одиниця | % |
| DAX | `First Pass Yield %` |
| Значення | 91.35% (144 353 з 158 026) |

Виріб, який пройшов тільки з другої спроби, у чисельник не потрапляє.

### K8. Retest Rate %

| | |
|---|---|
| Чисельник | вироби з двома й більше спробами тесту |
| Знаменник | вироби, які тестувалися |
| Одиниця | % |
| DAX | `Retest Rate %` |
| Значення | 8.65% (13 673 з 158 026) |

Загалом FPY і Retest Rate не мусять давати в сумі 100%. Так було б, якби виріб могли списати після першої невдачі без повторного тесту. У моїй моделі кожен виріб після невдачі йде на повторний тест, тому тут сума справді 100%.

### K9. Downtime Hours

| | |
|---|---|
| Формула | сума тривалості простоїв / 60 |
| Одиниця | год. |
| Джерело | `downtime_records` |
| DAX | `Downtime Hours` |
| Значення | 941.7 |

У таблиці простоїв немає продукту, тому фільтр за продуктом на цей показник не діє.

### K10. Downtime %

| | |
|---|---|
| Чисельник | хвилини простоїв |
| Знаменник | заплановані робочі хвилини: 628 днів-ліній × 660 хв × 2 зміни |
| Одиниця | % |
| DAX | `Downtime %` |
| Значення | 6.82% загалом, Day 6.14%, Night 7.50% |

### K11. Штуки на годину

| | |
|---|---|
| Формула | Good Units / фактичні години роботи (заплановані хвилини мінус простої) |
| Одиниця | шт./год. |
| DAX | `Good Units per Run Hour` |
| Значення | близько 11.95 загалом |

Лінії між собою за цим показником порівнювати не варто: вони випускають продукти різної складності, і лінія C (тільки HB-200) виглядала б гіршою без реальної причини.

### K12. Cost per Good Unit

Скільки коштує один придатний виріб.

| | |
|---|---|
| Чисельник | матеріали + праця + накладні, разом із витратами на вироби, які потім забраковано |
| Знаменник | Good Units |
| Одиниця | грн/шт. |
| DAX | `Cost per Good Unit` (`Total Cost` / `Good Units`) |
| Значення | 726.69 грн |

За продуктами (рахував у SQL): MS-100 609.36, DS-100 420.77, HB-200 1 815.25, FS-300 836.34.

Витрати на брак лягають на придатні вироби, тому показник і показує реальну ціну того, що можна продати. Показувати його за змінами не можна: у таблиці витрат немає розбивки за змінами, тому при фільтрі за зміною чисельник не змінюється, а знаменник змінюється, і результат виходить хибним. За лініями, продуктами й місяцями він працює.

### K13. Scrap by Stage %

| | |
|---|---|
| Чисельник | забраковані вироби, списані на етапі X |
| Знаменник | усі забраковані вироби |
| Одиниця | % |
| Джерело | SQL; у Power BI показано графіком `Rejected Units` за етапами |

Окремої DAX-міри для частки немає. Розподіл за етапами 1-7: 14.4, 22.3, 8.2, 20.6, 20.7, 8.9, 4.9%.

### K14. Scrap Cost

Скільки грошей втрачено на браку.

| | |
|---|---|
| Формула | сума по забракованих виробах: вартість матеріалів продукту × частка вартості, вкладена до етапу списання |
| Одиниця | грн |
| DAX | `Scrap Cost` |
| Значення | 4 128 816 грн |

Тут тільки матеріали. Праця й накладні, витрачені на забраковані вироби, не враховані, тому реальні збитки більші. У SQL і DAX значення можуть відрізнятися на 1 грн через округлення.

## Допоміжні показники

| Показник | Як рахується | Значення |
|---|---|---|
| Tested Units | `DISTINCTCOUNT(test_results[unit_id])` | 158 026 |
| Test Attempts | `COUNTROWS(test_results)` | 177 558 |
| Rejected Units | вироби зі статусом `Rejected` | 12 004 |
| Total Cost | `SUM(production_costs[total_cost])` | 111 823 760 грн |
| MoM Change % | (Good поточного місяця − Good попереднього) / Good попереднього | квітень порожньо, травень −1.24%, червень +2.03%, липень +3.51%, серпень −5.57%, вересень +0.43% |

Різниця між Tested Units і Test Attempts це якраз повторні спроби. Якби рахувати рядки, вийшло б 177 558 «протестованих виробів».

## Сценарна оцінка

| Показник | Формула | Значення |
|---|---|---|
| Estimated Savings | `Scrap Cost × 0.20` | 825 763 грн |

Це не факт, а гіпотеза: що буде, якщо брак зменшити на п'яту частину. Цифру 20% я взяв умовно, а вартість самих заходів не враховував.

## Що з чим звірено

Я порівнював DAX із SQL там, де був зріз для порівняння:

| Міри | Зріз |
|---|---|
| Planned Units, Good Units, Variance to Plan, Plan Achievement % | загалом і за місяцями |
| Tested Units, Test Attempts, First Pass Units, Retested Units, FPY %, Retest Rate % | загалом і за продуктами |
| Scrap Rate %, Downtime Hours, Cost per Good Unit, Estimated Savings, MoM Change % | загалом, а Scrap Rate % і MoM Change % ще й за місяцями |
| Downtime % | за змінами |

Cost per Good Unit за продуктами і Scrap Cost за етапами я перевіряв тільки в SQL. Розбіжностей, крім округлень до 1 грн у Scrap Cost, не було.
